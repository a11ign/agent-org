## What it is

A stacked pull request keeps its base branch. When the pull request it sits on squash-merges and its branch is not deleted, GitHub does not retarget the stacked one, so it stays aimed at a dead branch and merging it never reaches `main` (a11ign/agent-org#1749, 2026-10-18). This change makes ticket mode move such a pull request to the default branch itself, and says on the board what it cannot move. It also makes `onboard` and `update` keep the `github/gh-stack` extension a worker's `gh stack link` needs installed for the workers' account, and makes `doctor` check that extension and whether GitHub makes stacked pull requests available to each repository.

## Change

- `src/ticket-port/stack-retarget.ts` (new): a pure classifier, `baseKindOf`, and the sweep, `sweepRetargets`. The sweep reads each open pull request's base and state with the `gh` it is handed. Only a base that is the branch of one of the run's blockers is considered, since that is the base a stacked pull request has. Such a base that is the head of a merged pull request, with no open pull request on it, is moved with `gh pr edit --base <default>` and read back. A base on any other branch is the worker's own, and is left as it is. The head is never pushed, rebased or merged. A base whose branch is gone with nothing merged on it is not moved: it gets a note to retarget by hand. A base no pull request came from, and the default branch, get nothing. A pull request that cannot be read keeps its note and is asked again.
- `src/ticket-port/stack-extension.ts` (new, with its test): the extension's listing and install (`ensureStackExtension`), GitHub's stacked-pull-request answer for a repository (`stacksOf`: an empty or full list is enabled, its 404 is refused), and `asAccount`, which runs a `gh` runner as the workers' account by setting `GH_CONFIG_DIR` on this process for the one synchronous call and putting it back. The file names no `gh` command and spawns nothing: the runner it is handed is the existing `defaultGh`.
- `src/install/stack-account.ts` (new): the workers' account (`workerAccount`: the host file's `gh.workers`, else this environment's `GH_CONFIG_DIR`, else none) and the install command, so onboard, update and doctor name them the same way.
- `src/install/onboard.ts`: after the host file is written, installs the extension when it is not listed, and says so. A failure is said with the reason and the command to run by hand; it does not fail onboard.
- `src/install/update.ts`: keeps the extension present on every run, whether the checkout moved, did not move, or was deferred. A failure is said and never changes the exit code.
- `src/install/doctor.ts`: a `gh stack` check (fails with the install command when the extension is not listed for the workers' account), and a `stacked pull requests` check for each GitHub repository a clone names (fails naming a repository GitHub refuses, with the preview requirement and GitHub's page; fails with GitHub's answer when it cannot be read).
- `src/ticket-mode/pool.ts`: `retargetStacked()` runs the sweep over the open pull requests of each finished run that has a blocker with a branch, with a default-branch cache per sweep, and records the notes on the run when they change. A run that has not finished is not read or written.
- `src/ticket-mode/server.ts`: `startFeedbackSweeps(pool, every)` schedules the three feedback-cadence sweeps (`watchFeedback`, `releaseReviewers`, `retargetStacked`) at `FEEDBACK_MS`, each in its own try/catch, and `serve` passes `setInterval`.
- `src/ticket-mode/queue.ts`: an optional `retargets` field on an entry, by URL, set by `recordRetargets`; a retry or a review round drops it, as it drops `verdictNotPosted`.
- `src/ticket-mode/board-view.ts` and `src/ticket-mode/ui.html`: `retargetNote` shows the notes on a finished run as a waiting line. The run's status does not change for them.
- `src/ticket-port/stack-live-check.ts` (new, with its test) and `src/ticket-mode/stack-live-check-command.ts` (new), registered as `ticket:stack-live-check` in `src/commands.ts`: the live check of the retarget on GitHub, run from the branch before merge. A scratch branch stands in for the default branch; base pull request A is opened on it, stacked pull request B on A's branch, A is squash-merged into the scratch branch with its branch kept, the same sweep the board runs retargets B with the scratch branch as the default, and B's base and head are read back. Every branch and pull request it made is removed, even when a step fails. A pass prints `PASS: the stacked pull request's base is the scratch branch after its base merged, and its head did not move` and `cleaned up 3 branches and 2 pull requests`. The chairman runs it: `node src/bin.ts ticket:stack-live-check --repo a11ign/agent-org`.
- `src/ticket-mode/worker-files.ts`: the stack section says "your own pull request" (the acceptance criterion names that wording; it is a draft or ready as `tickets.drafts` says), and tells a stacked worker that agent-org retargets its pull request when the one it sits on merges, that a stale base is expected, and not to retarget, rebase, push or merge to fix it.

## Acceptance

Lint has no errors and typecheck passes. The affected tests pass, including the ticket-port purity test (no spawner or `gh` name in `src/ticket-port/` other than the adapter) and the gh-call ratchet (no new `gh` call outside `src/ticket-port/`). Removing each install-side call, the retarget sweep, or the board's render line fails the tests written for it.

Not exercised by a worker: the live check, which the chairman runs from this branch and quotes on the pull request (workers may not merge, and the live check merges only into its scratch branch). Not exercised before merge: the install on a clean host, and a worker's `gh stack link` on a fresh host. The ticket comment names who proves each of those, and when.
