The trace store keeps ONE line per event id: a corrected copy of an event replaces the stored one on disk instead of being appended behind it, so a sum over the file's lines is a sum over its events (agent-org#475, epic a11ign#4437, class `metrics-integrity`).

**The premise, as the row measured it and as it still holds at this head.** The store already refused an IDENTICAL copy of an id at write, and `readStore` already returned the last copy of each id, so a sum over `readStore` was right. What overstated was any reader summing the file's lines. The repeated ids are the corrections `appendToStore` appends on purpose. So the fix is that a superseded copy does not stay on disk, not a new refusal.

**What changes.**
- `appendToStore` (`store.ts`): a batch holding a copy that differs from the held one goes through `rewriteStore`, which streams the file once (each line kept as its own bytes), keeps each id at the position of its LAST copy (what `readStore` gives it), writes a temp file in the same directory and renames it over the store. A batch of only new ids is still a plain append, byte-for-byte on what was there and the same inode.
- **The other writer (`otel-receiver.ts`, `appendFileSync`) is protected by RE-READING, not by a lock.** The rewrite holds the old file open, so its inode stays readable after the rename; what was appended past the bytes the pass consumed is read from it (a) before the rename, and written to the temp file, and (b) after the rename, where it is appended to the new file. A last line with no newline is waited for (up to 1 s) and refused if it never completes, before anything is renamed. The receiver is not changed and takes no lock, so a rewrite never stalls a request, and a second REWRITER is told apart by the inode (the file replaced under a pass makes it start again, three times). **The window that remains** is microseconds wide: an `appendFileSync` that opened the old file before the rename and writes after the sweep (b) found nothing. A lock the receiver also honours would close it and put a wait into the receiver's synchronous request handler; this row does not take that trade.
- `node src/trace/trace.ts compact-store [--store <path>] [--dry-run]`: prints lines, distinct ids, lines it would remove and the count by `kind`; without `--dry-run` it copies the store to `<store>.bak-<UTC date>` FIRST (refused with `EEXIST` when that name exists), rewrites, and prints the same counts read back from the new file. A store with nothing to remove is not rewritten and gets no backup. An argument it does not know is refused, because a misspelt `--dry-run` would rewrite the store.
- The ingest state's `storeBytes` is restamped by every rewrite (`restampStoreBytes` in `ingest-state.ts`), because a smaller store than the state recorded reads as "deleted or replaced" and would start the next ingest cold, a full re-read of every transcript. This is the case for the command AND for an ordinary ingest whose GitHub batch supersedes after the state was saved.
- `readStore` returns the same events in the same order; the test pins it against the append-only log the old code would have written.
