A run whose worker declares a wait on another ticket gives up its slot and its files (A11-272). On 2026-10-25 A11-231 wrote `waitingOn: [{ ticket: "A11-229", until: "done" }]` and stayed `running`, holding its whole footprint, while A11-229 needed those files and stayed queued behind them: each waited on the other. Now, once the wait's first reading finds the ticket not done, the board records it as a blocker in the tracker, closes the run's workspace, and queues the ticket behind it with its Claude session (`stoppedForBlocker`). The run is held until the ticket is done, through the tracker's relation, or the stop's own record while the tracker does not list it. It waits for the ticket to merge and never stacks on it. When it starts again it resumes its own session. A ticket already done when first read is an ordinary declared wait, as before. And a run never holds its files against a ticket it waits on: one its worker declared a wait on, the ticket whose run has a pull request it waits on, or one of its blockers, each followed through the tickets those wait on. A fleet job or CI run names no ticket, so a run parked on one still holds its files against the others. The run timeline says "Queued again · a wait on another ticket".
