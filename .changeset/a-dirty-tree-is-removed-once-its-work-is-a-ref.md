`prune-worktrees --apply` removes a DIRTY worktree once its work is a ref it can read back, instead of leaving it for a person (a11ign/a11ign#4620, from incident #3846). A tree whose tracked files are clean and whose named branch still reads back from `refs/heads/<branch>` as the HEAD it is on is removed like a merged one: the branch survives, so its commits do. A tree with tracked edits is salvaged first: `git stash create` makes a commit of the edits, `refs/salvage/<tree>-<epoch>` is pointed at it and read back, and only then is the tree removed (a detached HEAD is pinned as `refs/salvage/<tree>-head-<epoch>` first). A salvage that cannot be written or read back leaves the tree DIRTY, with the reason on its report line. Every earlier refusal stands first (an ACTIVE tree, a HELD one, a live run, an untracked file that is not ignored), `--force` is never used, and the 25-removals-per-run limit, `nice` and the 250 ms pause are shared with the merged-tree path. The report names each salvage ref beside its tree, and `refs/salvage/*` is never pruned. The new path is on for `--apply` from the command line and off for a caller of `pruneWorktrees` that does not ask for it.
