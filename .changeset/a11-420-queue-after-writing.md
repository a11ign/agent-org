The New ticket dialog offers "After writing: Keep in backlog / Queue them" (A11-420). With "Queue them", `POST /api/writer` takes `after: "queue"` (any value other than `"backlog"` or `"queue"` is refused with a sentence naming both) and stamps the run with `queueAfter: { model, effort, plan: true }`, taken from the saved choice's `model` and `effort` at request time. When the run ends cleanly, the pool queues its tickets in the order the run made them, through a new server callback (`queueWritten`) that runs the same `refuseTaken` and `queueTickets` as `POST /api/queue`, and records `afterWriting` on the run: `{ queued: n }`, or `{ notQueued: "Written, but not queued: <why>. They are in the backlog." }`. A request stopped while its tickets are being read queues none: the run is asked again just before the add. It is all or nothing: a run that does not end cleanly, or files a ticket that cannot be read back, queues none. The dialog shows a Queue pill and "Write and queue", the run card adds "Queues them when done", and the Done notification marks each ticket the queue holds "Queued" and says they were queued only once the live queue holds them all, or shows the amber note with a "Queue them" button that queues the rest through `POST /api/queue`. A run queued before this change has no `queueAfter`, and its tickets stay in the backlog.
