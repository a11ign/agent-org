The org verifies its own After-merge checks, and the person's session is no runner of them (A11-302). A plan's `## After-merge checks` section names each line's runner as `board`, `agent` or `person`; `session` is refused, and so is any field that names the chairman's session, and every After-merge line must be in the section. `person` still needs an item of the escalation list. A `board` check names its source in `Observe:` with a pass condition and a window (`Pass: absent | present`, `Window: 30m | 6h | 7d`): `run-log`, `merge-queue`, `ci-history`, `doctor` and `release-assets` join the four event specs. A week-long check passes when its window closes clean and fails on the first breach, citing the event; the window begins when the ticket's change is in a release installed on the host, and a window the board cannot read or that closes without the event it waited for hands the check to an agent. An `agent` check is run by a verifier run the board starts once the change is installed (a Sonnet writer run in `verify` mode with its own limit that files no ticket), which records passed, failed or superseded with one line of evidence through `POST /api/after-merge/<KEY>/<n>` with `"by": "agent"`; a failure files its follow-up through the ticket writer. The board's After-merge list now shows only the checks that wait on the person; the org's checks are on their ticket's Run detail (`GET /api/queue/<KEY>`'s `afterMergeChecks`), the pool bar counts the open ones older than three days (`afterMergeOrg`), and `GET /api/after-merge/audit` says whether any is left on the retired runner. The checks open on the retired runner are re-read once by a planner pass (a `migrate` writer run) that rewrites each as a `board` or `agent` check, keeps it the person's with an item, or marks it superseded with a reason; any it does not answer goes to an agent. `GET /api/session-asks` no longer lists After-merge checks, a close by `session` or `board` is refused, and the escalation rule every brief quotes says the org verifies its own work.
