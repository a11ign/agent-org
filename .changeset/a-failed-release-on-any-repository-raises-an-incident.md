A failed `release.yml` run on ANY repository the org releases raises an incident naming the run's first error line within one tick, and a second consecutive failure wakes `ceo` (a11ign/agent-org#885 class 1, agent-org#887). `release-run-failed` read one repository, the project's, so five failed releases of agent-org's own `main` from 08:42Z on 2026-10-11 went unseen for 50+ minutes while the host stayed on v0.154.11. The reading is now one per repository (the project's and every `dora` entry, `releaseRepositories()`), each under its own discriminator `release-run-failed@<repo>@<first failed run of the streak>`, so one repository's failure neither hides nor re-keys another's and a later success clears only its own. The failed job's log is read for the first error line of the step that failed (`firstErrorLine`: the line before GitHub's `##[error]` marker that says "Process completed with exit code 1", never an earlier step's "0 errors"), and the detail and the incident quote it. A FIRST failure is an incident only: an `incident` item in the tracker carrying `Incident: incident:release-run-failed` and a `Release-failure: <repo>@<run>` line, filed once per streak (an open item for the repository, or a closed one for the same streak, files nothing) and closed when that repository releases again; the SECOND consecutive failure is also an order to `ceo`, keyed on the streak so a third is the same order and not another page. Cost: one `release.yml` runs call per released repository per tick (eight, 240 an hour of the core pool), one more for the failed job's log while a repository is failing, and the open `incident` list, which `readFleetBuildIncidents` already asks and `host/gh` answers from disk inside 20 s. A caller that gives `orgHealthReadings` only `releaseRuns` still gets the project-only reading it had, and the gate passes both.
