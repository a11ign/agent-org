The ticket board plans the tickets queued together in one planning run. It does so when `tickets.planner.run` names the new placeholder `{keys}`, which is filled with the batch's keys, separated by a comma and a space. A batch is the tickets one press of Queue plans first, at most 8 to a run, in queue order. While the run works, each ticket of the batch shows as Planning, links to the run's one terminal, and the batch holds one worker slot. The run writes `<dir>/<KEY>/` per ticket, holding its plan files or a `QUESTION.md`, and `<dir>/order.json`, giving each ticket's repository and the tickets of the batch it waits on. A ticket with plan files has them attached and is queued again to be worked, with its planned repository recorded on its queue entry as `plannedRepo`. A ticket with a question, or with nothing, ends as Needs you, and the rest carry on. The board records the order in Linear as "blocks" relations through a new optional `TicketSource.addBlockers`, and skips a relation Linear already has. It writes no relation from an order that names a ticket outside the batch, a ticket waiting on itself or a cycle, and logs why. Stop on any ticket stops the whole run, and Retry plans a ticket again on its own. An instruction that names only `{key}` plans every ticket alone, as before, so a host file that does not change keeps today's behaviour. One change reaches every run: a run queued while the board was reading blockers, such as a ticket queued again by its batch, now waits one pass for its own blockers to be read before it starts, where before it could start with them unread.
