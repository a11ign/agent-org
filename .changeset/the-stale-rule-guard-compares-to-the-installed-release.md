The stale-rule guard compares a claim's rule files with the newest release the host can run, not with `origin/main`, and a claim-refusal storm is raised. `src/row-claim/stale-rule-guard.ts` counted `HEAD..origin/main` on the rule modules, so a rule file merged to `main` and not yet released (v0.154.11 was the newest while releases were failing) refused every claim: 163 refusals between 08:09 and 09:15 on 2026-10-11, and no worker started, the one that would have fixed the outage included. It counts `HEAD..<newest release tag>` now (the newest `vX.Y.Z`, ordered numerically as `update-tool` selects), so a checkout behind a RELEASE still refuses and names what that release moved, while a rule file only `main` holds is let through and logged by name (`stale-rule-guard: origin/main holds N rule file(s) that vX.Y.Z does not (...)`). A checkout that holds no release tag cannot tell the release from `main`: it is let through and logged, never refused and never silent; with no `origin/main` either it is still CANNOT ASK. The installed (`node_modules/`) layout still compares with `main`. `org-health` raises `claim-refusal-storm` when more than 10 claims were refused inside 15 minutes, naming the most frequent reason, read from `claim-refused` lines of the failure ledger (the recorder at the claim's refusal exit is a separate row). a11ign/agent-org#885 class 2, agent-org#889.
