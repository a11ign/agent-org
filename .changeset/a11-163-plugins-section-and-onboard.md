The Settings page has a **Plugins section**, onboard **installs and enables** the plugins it chose, and doctor prints **a section per plugin**. The page lists every concern (Tracker, Code host, Publisher, Reviewer, Exposure, Messaging) with each plugin's name, agent-org's version, its contract version and its state in words (`enabled`, `disabled`, `not installed` or `failed`). It is its own call (`GET /api/plugins`), so the rest of the page is drawn while a plugin's checks run, and a failed call is said inside the section only. Enable, Disable, Install and Uninstall (`POST /api/plugins/action`, local instances only) are the plans of `agent-org plugin`, written through the one writer: the readers' verdict, the backup and the `base` check against a concurrent change all hold, the only tracker and the only code host cannot be disabled (the control is drawn off with the CLI's own sentence beside it), Uninstall and an Install that replaces another plugin ask first, and the switch keeps the settings both plugins declare. Configure opens the plugin's own settings from its schema, edited in place as before; `provider` and `enabled` are shown by the state and the controls. **A secret is never typed in the page**: a plugin that needs one shows the exact command that sets it with a copy button (a manifest's secret setting must declare `setCommand`, or the registry refuses it by name), and has no Install button but its install command. A required concern with no plugin enabled says "No tracker enabled: the board cannot run" (or "No code host enabled: …") with the command; an optional one says "None" with how to add one; a plugin that failed to load is a red row with doctor's reason and fix, word for word.

**Onboard installs and enables what it chose.** A fresh machine ends with explicit `linear` and `github` blocks (`provider` and `enabled: true`), and with one for each optional concern whose choice is not `none`, so `agent-org plugin list`, `disable` and `config` and the page read them; it says `installed linear as the tracker` before it runs that plugin's steps, and keeps a key the host file already holds. A profile's `provider` is checked against the registry (a bundled plugin of the concern, not a fake, plus `none` for a publisher or reviewer) and the questions offer the registry's plugins; the profile keeps schema 1 and its block shape. **Doctor prints a section per plugin**, in concern order, each headed `tracker: linear (enabled, contract 1.1, plugins/linear)` with the plugin's checks beneath and the concern's row closing it; the machine's checks come before the sections, and the exit status is unchanged.
