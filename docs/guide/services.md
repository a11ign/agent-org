# Services and updates

[Back to the README](../../README.md).

| command | what it does |
|---|---|
| `agent-org start [herdr\|instance\|ui\|terminal\|auto-update\|watchdog] [--move]` | Registers the service to start at login and starts it: a launchd user agent on macOS, a systemd user unit on Linux. The herdr service runs `herdr --session <tickets.herdrSession> server`, which holds every worker's pane, in a unit of its own (`agent-org-herdr.service`): the instance and the terminal `Want=` it and start after it, and nothing `Requires=`, `BindsTo=` or `PartOf=` it, so restarting the instance, the ui or the terminal never reaches a worker. `start herdr` starts the unit and never restarts it; while a herdr server runs outside the unit (one an older instance started in its own cgroup, or in the transient scope the instance once made), it refuses and says how many runs are live, and `start herdr --move`, run once at a quiet moment, stops that server, starts the unit (every pane restarts once) and retires the `KillMode` drop-in and the gh-wrapper watchdog on their proof. The instance service runs `ticket:serve`, the queue and its workers. The ui service runs `ticket:ui`, the page. The terminal service runs herdr web ui for `tickets.herdrSession` on `127.0.0.1`, on the port `tickets.terminal` names (`7318` by default). The auto-update service runs `agent-org update` every ten minutes: a systemd timer on Linux, a launchd `StartInterval` job on macOS. The watchdog service runs `agent-org ticket:watchdog` every minute, the same way, and restarts the instance when it stalls ("[The watchdog and the board's health](troubleshooting.md#the-watchdog-and-the-boards-health)" in Troubleshooting); `agent-org update` registers it on a machine that runs the instance and has none, and `agent-org stop watchdog` turns it off. The service is `instance` when you name none. Starting a service writes its unit again, which fixes a unit systemd refused. With the Tailscale exposure (`tickets.serve: "tailscale"`, or `tickets.providers.exposure`), the ui and terminal services are also served on the tailnet with `tailscale serve --bg`, on its `tailnetPorts` (`tickets.servePorts`), after the plugin's checks pass: tailscale is Running with a DNS name, and the port is free of Funnel and of other entries. A check that fails names its fix, and the service is not started. The instance and auto-update are never served. A service that is started but cannot be served on the tailnet says so, and it stays on loopback. |
| `agent-org stop [herdr\|instance\|ui\|terminal\|auto-update\|watchdog]` | Stops the service and keeps it from starting at login. `agent-org stop auto-update` turns automatic updates off. With the Tailscale exposure, the ui and terminal services also lose their own tailnet entry, on their own port only: no other entry on the host is named, and no Funnel is changed. If that entry cannot be removed, the service stays stopped and the command says how to remove it. |
| `agent-org status [herdr\|instance\|ui\|terminal\|auto-update\|watchdog]` | Prints whether the service is running, stopped or not registered, and the reason when systemd will not load its unit. It exits 3 when the service is not running. |
| `agent-org update` | Moves the install to the newest release, or to `--version vX.Y.Z` (or the `toolVersion` the host file pins), and restarts the instance and the ui if they were running. `--channel main` follows `main` instead of releases. The release is built into its own folder, `tool/versions/<tag>`, and `tool/current` is pointed at it; it applies whatever is live, because a run keeps the folder it started on and herdr is not restarted. A release whose changeset starts `Breaking:` with runs live is built and waits instead (see "Kept up to date"); `--force` applies it at once. Before it restarts the instance it waits for any run that is still `starting`, for at most two minutes (not with `--force`), so a run that has not yet opened its agent is not queued again by the restart (A11-294). A release that ships the board UI's build has it downloaded from its GitHub Release, checked against its checksum and unpacked into the folder before `current` moves (see "Install"); a release whose build is not attached yet, or whose checksum does not match, is refused and `current` stays, and the next run tries again. It keeps the `github/gh-stack` extension present on every run; a failure is said and does not change its exit code. It also keeps herdr's side current on every run, in the auto-update log: it reads `herdr integration status` and re-installs the `claude` and `codex` integrations when either is outdated or missing, moves the herdr plugin agent-org installed (`devswha/herdr-web-ui`) to its newest release tag with `herdr plugin install <repo> --ref <tag> -y`, and restarts only the terminal service when the web UI moved. It finds a plugin by its repository, uninstalls the older copies a renamed manifest id leaves, and says a plugin step that does not take once, with herdr's output, exiting 1 for that run (see "herdr's integrations and plugins are kept current too"). It records the newest versions it saw in `~/.agent-org/herdr-status.json`, which `doctor` reads. It never upgrades or restarts herdr. It also refreshes each conventions plugin in `tickets.plugins` whose marketplace is a GitHub repository (`claude plugin marketplace update`, then `claude plugin update`) at every update, and says the version a plugin moved to: a new run or round gets the new copy, and a running session keeps the one it started with. |

The macOS service writes its log to `~/.agent-org/logs/<service>.log`. On Linux, read it with `journalctl --user -u agent-org-<service>`.

**Kept up to date.** The auto-update service runs `agent-org update` every ten minutes, following `release` or, when `~/.agent-org/update-channel`
says `main`, `main`. A tag fetch with nothing new restarts nothing. A new release is built into `tool/versions/<tag>` and `tool/current` is pointed at it; the
instance and ui restart onto it at once, whatever is live, because **a run is pinned to the version it started on**: its hooks and its brief's commands (the Stop
hook, `pr:open`, `ticket:worktree`) name that version's folder, written at each start and each round. A run that started on `v0.273` keeps calling `v0.273` until it
ends; a new round of it (a review round, an answer, a re-queue) picks up the newest. An answered park and a talk session keep the version they had. A folder is
pruned only once no run that is live or parked names it (and never `current`, nor the folder of the process pruning). `doctor` lists each such run's version.
The first update from a checkout install (the clone `install.sh` used to make, or a hand-made one) seeds the mirror from the checkout's remote, builds the first folder, and rewrites the
units, the launcher and the host file's `tool` once to run through `tool/current`; the checkout is left as it is, and runs that started on it keep calling it.
Each run writes `~/.agent-org/update-status.json`, which `doctor` reads to say how far behind the install is, and since when.

**herdr's integrations and plugins are kept current too (A11-184).** Each `agent-org update` run ends by reading `herdr integration status` and re-installing the `claude` and `codex`
integrations when either is outdated or missing (a herdr upgrade leaves them outdated), then moving the herdr plugins agent-org installed (today `devswha/herdr-web-ui`) to their newest
release tag, never a branch, so a broken upstream `main` is never pulled. When the web UI moved, only the terminal service restarts, and only if it was running; the instance and the ui are not
touched by this step, and no live run is. **A plugin is found by its GitHub repository, never by its manifest id (A11-287):** a release can rename its id (`devswha/herdr-web-ui` went from
`devswha.herdr-web-ui` to `devswha.ovis` at v0.4.16, and herdr then lists both), so of the entries that share the repository the one on the highest release tag is the current one, and the terminal service
runs its `plugin_root`. Once the terminal runs the current copy (restarted, or no terminal service is registered; a stopped one keeps its unit's old path, so the older copy stays and `doctor` warns), upkeep runs `herdr plugin uninstall <id>` for each older copy. **A step that does not take is said once:** a plugin install that fails or leaves
`plugins.json` without the tag, or an uninstall that leaves the entry, is one error line in the update log with herdr's own output (the last 20 lines, at most 2,000 characters), it is recorded in `herdr-status.json`,
and that update run exits 1. Later runs on the same release run nothing and add no line; a newer release is tried once, and a hand fix ends the record. Each change is a line of the update log (`journalctl --user -u agent-org-auto-update` on Linux, `~/.agent-org/logs/auto-update.log` on macOS). **A herdr
upgrade is a person's step:** restarting herdr ends every pane, so auto-update never installs, upgrades or restarts herdr (A11-223); herdr moves only when a release changes the version it pins (`TOOL_HERDR_VERSION`, with `HERDR_VERSION` in `install.sh`),
and then `doctor` warns on each machine whose herdr differs and prints the steps (at a quiet moment, with no live run on the board, the pinned download command, then `agent-org stop herdr` and `agent-org start herdr`). It does not suggest
`herdr update`, which installs the newest version and not the pin.

**A breaking release drains.** A release marks itself breaking with a changeset whose first line starts `Breaking: ` (the repository is 0.x, where `minor` is not a
signal; `.changeset/README.md` says how). When one is in the range of an update and runs are live, `update` builds the folder and writes `~/.agent-org/update-drain.json`;
it swaps nothing. While that file exists the instance starts no run and no round, and the Board says so in a banner (`Updating to v0.280 (breaking): no new runs start; 2 runs finishing; forced at 14:30`):
each live run reads "finishing before the update" and each queued one "waits for the update". When the live runs have all finished, the next update applies it. After
`tickets.updateMaxDeferHours` (2 by default) the instance stops the runs still live and queues them again, each keeping its Claude session (`stopped for the update at 14:30 and re-queued;
resumes on v0.280`), and runs the update at once; they resume as rounds on the new version, and the banner clears when the update has applied. `agent-org update --force` applies a breaking release
without draining.

**A restart leaves the workers alone.** The workers run in ticket mode's herdr server, which runs in a systemd service of its own, `agent-org-herdr.service`
(launchd: `io.github.agent-org.herdr`), not in the instance's. The instance and the terminal `Want=` it and start after it, and nothing restarts it with them, so
restarting or updating the instance never stops a worker. The instance that starts up adopts the runs herdr lists and carries on watching them: it sends their panes
no key, no prompt and no second start, and a reviewer it started for a head is not started again. Herdr, not the queue file, says whether a run survived: every run the file holds as
`starting` or `running` is looked up by its herdr name, so a run caught in its first minute, before its workspace was recorded, is adopted too, and its card says `re-adopted after a
restart`. A run herdr does not list, or lists with its pane gone, ends `crashed: lost in a restart` and is queued again once if the board has no pull request on record for it, unless it was still `starting` (its agent never opened): that run has nothing to lose, so it is queued again as it was, with its round, and not ended (A11-294). `agent-org update` holds the restart of the instance until no run is `starting`, for at most two minutes. A run already marked
crashed whose pane herdr lists `working` is taken back on the next watch pass, and the card says so (A11-240). A work run is told, in its brief, which pull requests its ticket already has on the code host (those whose `Closes` or `Refs` line names the ticket), and Respond answers an open one the record never held (`pullsNaming`, `src/ticket-mode/opened-pulls.ts`, A11-240). A herdr server an older instance started is still outside that
unit: `agent-org doctor` fails `herdr scope` for it, and `agent-org start herdr --move`, run once at a quiet moment, moves it.

**Two instances review a head once.** Every instance sweeps the open pull requests of the repositories it clones, and starts a reviewer on each new head whose required checks are green. The required checks are the ones GitHub says the pull request's base requires, from its branch protection rules and its rulesets (`isRequired`), read only when the checks are not all green: a failing check that is not required holds nothing, and the reviewer's brief names it ("These checks failed at this head and are not required"). When the list cannot be read, or the base requires nothing, every check counts. Two instances on one project (the agents host and a laptop, say) would both see a new head before either had posted, so before a reviewer starts, the instance claims the head on GitHub: a commit status `agent-org/review` on the head, which every instance can read, whose description names the instance and the time (`claimed by <instance> at <time>, lease 60 min`). An instance that finds another's live claim on the head starts nothing, and `ticket:review` says which instance holds it. A claim is live for its lease (`REVIEW_LEASE_MINUTES`, 60 minutes) and has no verdict; a claim older than that is taken over, and the board says so. The verdict door sets the claim to the verdict when the review posts (`convinced by <instance> at <time>`), so the head reads as finished. The instance's name is `tickets.instance`, which defaults to the machine's host name. The claim is written as the `reviewer` role and read back as the role the instance's own `gh` runs as (`scheduler`), and its read is made past the `gh` wrapper's read cache, since a write by one account does not drop another account's cache. `agent-org doctor` asks each of the two whether its App can use commit statuses (`commit statuses reviewer` must have *Commit statuses: Read and write*, `commit statuses scheduler` at least *Read-only*), by reading the App's installation, and names the exact permission to grant when it cannot. A claim GitHub refuses to take starts no reviewer: the head is not recorded as started, the next sweep tries it again, `ticket:review` can start it once the claim succeeds, its pull request's line reads `cannot claim for review: <reason>`, and the board shows one warning for all such pull requests. The one exception is an instance that is alone: when the write was refused after a clean read, the head read again shows no other instance's live claim, and no other instance's status under `agent-org/review` has been seen on any head within the lease, the reviewer starts anyway, the line reads `reviewing without a claim: <reason>`, and the board's warning says so. With a second instance in sight it does not start.
