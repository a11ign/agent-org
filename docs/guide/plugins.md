# Plugins

[Back to the README](../../README.md). How a plugin is built is in [plugins/README.md](../../plugins/README.md); the keys each one reads are in [Configuration](configuration.md).

Every external concern of ticket mode is an **agent-org plugin**: a code module behind a versioned contract (a "Claude plugin" is something else: `tickets.plugins` lists those). There are six concerns: the tracker, the code host, the publisher, the reviewer, the exposure and messaging. A plugin's settings are the block of its concern under `tickets.providers`: `tracker` (`linear`, the bundled plugin in [`plugins/linear`](../../plugins/linear), which brings its settings schema, its doctor checks, its onboard steps and its agent tooling: the Linear MCP, its read-only connectors and the tools a new-ticket run files with), `codeHost` (`github`, the bundled plugin in [`plugins/github`](../../plugins/github), which brings the settings `identity`, `gh` and `stack`, its doctor rows (the stacking extension and the stacked pull requests of each GitHub clone) and its onboard step), `publish` (`slack`, the bundled plugin in [`plugins/slack`](../../plugins/slack), which brings the settings `run`, `model`, `effort` and `connectors`, the `post-pr-to-slack` skill its publish run uses, its doctor rows and its onboard step, or `none`), `reviewer` (`atomic`, the bundled plugin in [`plugins/atomic-reviewer`](../../plugins/atomic-reviewer), which brings the gate's codex reviewer with its doctor rows (the gate loads; Codex is installed and logged in) and its onboard step, or `none`) and `exposure` (`local`, the default, in [`plugins/local`](../../plugins/local), or `tailscale`, in [`plugins/tailscale`](../../plugins/tailscale)). Messaging is the sixth concern, and it is configured in the primary project's `.agent-org/project.json` `messaging` key and not in a block: `telegram` is the bundled plugin in [`plugins/telegram`](../../plugins/telegram), with the settings `tokenFile`, `chairmanFile` and `announcementsFile`, and `enabled` (absent is true) there too. In a block, `provider` names an installed plugin, `enabled` (absent is true) turns it off without forgetting its settings, and the rest are the plugin's own settings, each refused by name when the plugin does not declare it. Exactly one tracker and one code host must be enabled, so `enabled: false` on either is refused by name; a disabled publisher publishes nothing, a disabled reviewer starts none, and a disabled exposure serves the board on loopback only. A plugin that implements a contract major this agent-org does not read is refused by name, at start and in `agent-org doctor`. No concern's code is built into core: the tracker moved in A11-159, the code host in A11-160, the exposure and messaging in A11-162 and the publisher and the reviewer in A11-161, so core runs whichever bundled plugin a host enables (and `none`, for the publisher and the reviewer, is the absence of an enabled one). The publisher plugin builds the publish run's brief, names its connectors, model and effort and reads its outcome, over the publish protocol that stays core's; the reviewer plugin's folder is `plugins/atomic-reviewer` but its name stays `atomic` (its manifest's `agentOrg.name`), so no live host file changes. **Reviews required** (`tickets.providers.reviewer.required`) is a per-machine setting of the reviewer concern, valid under any provider, `none` included: absent, it is true when the block (or the old `tickets.reviewer`) names a reviewer plugin, enabled or not, and false when it names none or there is no block, so a machine that runs the atomic reviewer requires it and one with no reviewer (where people review) does not; `agent-org plugin config atomic required=false` sets it, and uninstalling the reviewer keeps an explicit one. When it is required and the reviewer is off (none, switched off, or one whose gate does not load) the Board shows the banner "Reviews are required and the reviewer is off", each open pull request's line says "waiting on the reviewer (off)" and `agent-org doctor` fails with the command that enables it (`agent-org plugin enable atomic`, or `install` when none is installed); when it is not required and there is no reviewer, each run's open pull requests say "awaiting your review" and nothing else is shown. Disabling the reviewer stops new reviewer starts only (a reviewer still running finishes and posts), and enabling it resumes on the next board start, with a reviewer on the current head of every open pull request, once per head. **When a run can be published** (`tickets.providers.publish.when`) is a per-machine setting of the publisher concern in the same way, valid under any provider, `none` included, and kept when the publisher is uninstalled: `ready-to-merge` (absent) or `awaiting-review`, for a machine where people review; `agent-org plugin config slack when=awaiting-review` sets it, `agent-org doctor`'s publisher row says it, and anything else is refused by name. A publisher that is installed and disabled hides the Publish buttons and says "publishing off" on each run it would offer for Publish; enabling it publishes nothing retroactively. The tracker, the code host, the exposure and messaging moved earlier (core asks the activated exposure for the names, addresses and serve calls the board used to take from Tailscale, and the activated messaging plugin for the provider; `src/plugins/boundary.test.ts` refuses the `tailscale` command, a tailnet host or `api.telegram.org` in core): core runs whichever bundled tracker or code host plugin is enabled, imports no plugin's code and names no Linear endpoint or tool (`src/plugins/boundary.test.ts` refuses both), and `agent-org plugin disable linear` and `disable github` are refused while each is the only one of its concern. A11-160 moves the code host's GitHub calls into `plugins/github` in steps, each its own pull request (so far: ticket mode's reads of a pull request, the routing `gh` wrapper and App tokens, and a red check's log and rerun, the review claim and the verdict door the reviewers post with, the last behind code host contract 1.5); `docs/gh-call-baseline.json` lists the files that still call `gh`, `src/packaging/gh-call-ratchet.test.ts` refuses a call in any file outside `plugins/github` that the baseline does not allow, and the baseline only goes down. A block left out takes its plugin's default, which `agent-org doctor` says. The old keys, such as `tickets.linearKey`, `tickets.workingState`, `tickets.publish`, `tickets.reviewer`, `tickets.port` and `tickets.serve`, are read as aliases for one release: `agent-org doctor` names the place each one moves to, and `agent-org doctor --fix` moves them, keeps a backup of the host file beside it, and writes nothing unless the moved file reads the same settings.

`agent-org plugin list|install|enable|disable|uninstall|config` manages them. `enable <name>` of a plugin the concern's block does not name SWITCHES the block to it when the block names another plugin of that concern (`agent-org plugin enable local` on a tailscale host): it keeps each setting both plugins declare, drops the rest (`tailnetPorts`) and a `terminal` that is the outgoing plugin's own address, and says which. The plugin it leaves is RELEASED first, while it is still the enabled one and after the readers have accepted the change: `release` takes what the plugin put on the machine off it (Tailscale removes the two entries it serves for this board, and no other), and a release that cannot (Tailscale not running) refuses the change by name and writes nothing, so the host file and the machine never disagree. `disable`, `uninstall` and `install --replace` release the same way. After a switch, restart the instance, the page and the terminal (`agent-org start instance`, `agent-org start ui`, `agent-org start terminal`): on `local` they listen on loopback and serve nothing, and `agent-org doctor` is green. `list` shows each concern with the plugin enabled for it and every plugin known for it (bundled in `plugins/<folder>`, or a fake for tests), with its contract version and any refusal. `install <name> [--set key=value] [--replace]` writes the plugin's block (it is refused by name when the block names another plugin, unless `--replace`); `enable <name>` and `disable <name>` set `enabled`; `uninstall <name>` removes the block, and the concern falls back to its default (refused for the tracker and the code host, which must keep one); `config <name> [key] [key=value] [--unset key]` shows or sets the block's settings, never printing a secret, only the path of its file. Each write goes through the Settings page's own path: it keeps the file's layout and your `_` notes, is refused when the readers would refuse the new file, and leaves `host.json.bak` beside it. A key the schema marks dangerous needs `--confirm`. A concern still read from an alias is refused a write, naming `agent-org doctor --fix`, and messaging is written to the primary project's `project.json` through the same path (`telegram` there takes `enabled`, `tokenFile`, `chairmanFile` and `announcementsFile`; `uninstall` removes the whole `messaging` key, its `summary` and `milestones` too, and `project.json.bak` holds it). The Settings page's **Plugins section** (A11-163) is where the same plugins are listed and controlled. It is its own call (`GET /api/plugins`), so the rest of the page is drawn while a plugin's checks run and when they fail. It groups the plugins by concern (Tracker, Code host, Publisher, Reviewer, Exposure, Messaging), and each row says its name, agent-org's version, its contract version and its state in words: `enabled`, `disabled`, `not installed` or `failed`. The controls are the CLI's own plans, written through the one writer (`POST /api/plugins/action`, local instances only, refused with the CLI's sentence and nothing written when the file changed since the page read it): Enable and Disable (Disable on the only tracker or code host is drawn disabled, with the reason beside it), Install on a plugin that is not installed (one that replaces another plugin of the concern asks first, naming the plugin and the settings it drops, and keeps the settings both declare), Uninstall (asks first), and Configure, which opens the plugin's own settings from its schema, edited in place as before (`provider` and `enabled` are shown by the state and the controls and are not drawn as settings). A change is in force when the board restarts, which the page says. **A secret is never typed in the page**: a plugin that needs one shows the exact command that sets it with a copy button (each secret setting of a plugin's manifest declares it as `setCommand`), and a plugin that needs one is installed with `agent-org plugin install` or `agent-org onboard`, so it has no Install button but its install command. A required concern with no plugin enabled says "No tracker enabled: the board cannot run" (or "No code host enabled: …") with the command that enables or installs one, and an optional one says "None" with how to add one. A plugin that failed to load is a red row with the reason and the fix, and the other rows are drawn. A remote instance's Plugins section is read-only: its files are changed on that machine.
