# Troubleshooting

[Back to the README](../../README.md). `agent-org doctor` is the first thing to run.

| command | what it does |
|---|---|
| `agent-org doctor` | Checks Node, the launcher on `PATH`, the host file, `herdr`, the Linear key, and that `claude mcp list` shows `linear` connected. It checks whether each service is registered and answers on its port. For the web terminal, it checks that `tickets.terminal` is on this machine's loopback and that herdr web ui answers `/api/health` there. With the atomic reviewer, it checks that `codex` is on `PATH` and logged in (`codex login status`). For auto-update, it checks that the service is registered. A unit systemd will not load (`bad-setting`) is reported with the line systemd refused. The agent-org plugins are printed as one section each, in the order tracker, code host, publisher, reviewer, exposure and messaging: a header names the concern, the plugin, its state, its contract version and where its code lives (`tracker: linear (enabled, contract 1.2, plugins/linear)`), the plugin's own checks are indented beneath it, and the concern's row that summarises them closes it. A disabled plugin's section says what the board does without it, a concern with none is `publisher: none`, and a plugin that failed to load (the registry refused its package, it implements a contract major agent-org does not read, or its import or `create` threw) is a FAIL row in its own section with the reason and the fix, which the Settings page shows word for word. What the registry refused, which names no concern, is the section "refused by the registry". Doctor prints the fix for each check that fails, and exits 1 when any check fails. It checks each plugin `tickets.plugins` names, as a worker's session gets it: one that does not load, or whose declared contract does not match the host's keys, fails under its own name (`plugin <name@marketplace>`), and one that is fine is listed as ok. When Claude Code's install record cannot be read, each plugin is shown as not checked, which does not fail. The exposure plugin the host enables adds its own rows: with Tailscale, it checks tailscale (Running, with a DNS name) and each served port (its `tailscale serve` entry, that it is not on Funnel, and that it answers under the machine's name); with the local exposure, that the instance and the page answer on `127.0.0.1` and what the terminal address is. The messaging plugin adds its rows too (for Telegram: the token file is readable by no one else, and the chairman has paired). herdr's `claude` and `codex` integrations are a row each (`herdr claude integration`): a FAIL when outdated or not installed, with `herdr integration install <name>` as the fix. A row printed `WARN` is not a failure and does not change the exit code: `herdr version` warns when herdr is not the version this release pins, older or newer, with the steps a person takes to bring it there (a herdr upgrade restarts every pane, so `update` never does it); a missing herdr fails the `herdr` row, whose fix is `agent-org onboard` and the pinned download command for the machine, and `herdr plugin devswha/herdr-web-ui` is ok at its newest release tag, warns when the plugin is behind it or an older copy of it is still listed (naming `herdr plugin uninstall <id>`), and fails while the last `agent-org update` recorded a step that did not take for the newest release (naming the command and the last line of herdr's output). It also says how many releases behind the newest one the install is, and since when (`update lag`; it fails once the install has waited past `tickets.updateMaxDeferHours` and an hour's grace). It checks the `github/gh-stack` extension a worker's stacked pull request needs, for the workers' account, and fails with the install command when it is missing. Where a clone is on GitHub it also checks that GitHub makes stacked pull requests available to that repository: stacked pull requests are a GitHub preview, so a repository GitHub refuses is named, with the preview requirement (`stacked pull requests`). `herdr scope` passes when the herdr server of the instance's session runs in `agent-org-herdr.service`, and fails when it is inside the instance's cgroup or in the old transient scope, with the fix `agent-org start herdr --move`; the `keep-herdr.conf` and `gh-wrapper watchdog` rows fail while either guard is still on disk on such a host. It lists each live or parked run with the version of agent-org it started on beside the instance's (`A11-170: v0.273.0 (instance v0.280.0)`, or `all 2 runs are on v0.280.0`), fails the `plugin copy` row when a refresh rewrote the plugin folder a live run's session uses, and says a breaking update that is draining (`update drain`). The `ui build` row (A11-191) is `ok` when the build `/` is served from is there, and `ok` with "this version ships no UI build" for a release before the marker; it is a `WARN` when the running version's release ships a build and none is found, naming the folder it looked in, with `agent-org update` (which fetches it) as the fix, or `pnpm ui:build` in a checkout. |

## The watchdog and the board's health

The board keeps rolling figures of its own health and serves them at `GET /api/health` (A11-363), beside the event-loop readings and the calls that held the loop (A11-282): under `figures`, the event-loop lag p50 and p99 over the last minute and the last hour (`loop`), the synchronous calls that held the loop 100 ms or more in the last hour (`syncHolds`), the Linear and GitHub calls and how many failed per 100 over the last hour (`calls`), the time since a run last started, the queued entries that could start now and the free slots (`runs`), and the time since a `fill()` pass last completed with the reason the latest pass returned early, if it did (`fill`). A call fails when it did not reach the service or the service failed it (a reset socket, a timeout, a 429 or a 5xx; a `gh` that printed that); a 404 is the service answering. `watchdog` is the watchdog's record, absent until it has restarted the board once. The figures are as old as the board thread's last snapshot (`boardSnapshotAgeMs`), which a held board thread stops refreshing.

The watchdog is `agent-org ticket:watchdog`, run every minute by the `watchdog` service (a systemd timer, a launchd interval job on macOS), so a board whose loop is held cannot hold it. It restarts the instance when queued runs could start, slots are free and nothing has started for 10 minutes; when no `fill()` pass has completed for 5 minutes; or when `/api/health` has not answered for 30 s. It leaves alone an instance that is stopped, one that became active less than 2 minutes ago, and a restart's reason while a run is still starting (its agent is not open yet) for up to 2 minutes. Each restart is a line of the watchdog's log (`journalctl --user -u agent-org-watchdog` on Linux, `~/.agent-org/logs/watchdog.log` on macOS) with its reason, and is counted in `tickets/watchdog.json` in the state directory. A `watchdog.json` that cannot be read is never written over: the watchdog sets it aside as `watchdog.json.unreadable-<time>`, says so as an error, and starts a record of its own; until then the board asks for no defect ticket from it, and `doctor` and the sidebar say the record cannot be read. More than 2 restarts in one hour make the board ask its ticket writer for one defect ticket for that hour, however many restarts it holds. A restart keeps running runs running: the workers live in herdr's own service, the instance takes every pane herdr lists back when it starts, and an instance that is stopping starts nothing more and waits up to 15 s for runs whose agents are not open yet.

`agent-org doctor` and the board's sidebar show the figures, and flag a loop p99 over 100 ms (in either window), call failures over 1 in 100, and any watchdog restart in the last day.
