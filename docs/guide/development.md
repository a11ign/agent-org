# Working on agent-org

[Back to the README](../../README.md). The commands are in [AGENTS.md](../../AGENTS.md).

## Source is TypeScript

**Every source file is `.ts`, run by `node file.ts` with no loader** (ADR 0043, a11ign/a11ign#3550, #4389). Node 24 strips the types itself
(`process.features.typescript` prints `strip`), `engines.node` is `>=24`, and `tsx` is not a dependency. `src/packaging/mjs-ratchet.test.ts` judges the
`.js`/`.mjs`/`.cjs` files against `mjs-ratchet.baseline.json` and fails on a file the baseline does not list, so the count can only go down and there is no raise.
The mapping from `@ts-check` JSDoc to types is in the ADR's table. Type stripping erases syntax and nothing else, so `enum`, `namespace` and parameter properties are
refused (`erasableSyntaxOnly`), and a relative import names the `.ts` file.

**One limit: Node refuses to strip types under `node_modules`** (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`, measured on 24.21.0 and decided on the real path). So the tool
runs from a checkout outside `node_modules`, which is what `host/agent-org` and the `AGENT_ORG_TOOL` clone are; a copy a package manager installs under `node_modules` can
be read but not run.

## The board UI package (`ui/`)

`ui/` is the board UI's foundation (A11-188, part of A11-187): **Astro with React islands**, strict TypeScript, built to **static files** (`output: "static"`, `base: "/"`) with no adapter and no server of its own. The instance's server stays the only server. It is the board: `ticket:ui` serves it at `/` (A11-202, which retired the old page, `src/ticket-mode/ui.html`, and moved the build up from `/next`). Its pages are the Atomaut shell (A11-194): the sidebar, the instance switcher, the connection pill and the design tokens, with the Tickets (A11-196), Runs (A11-197), Run detail (A11-198), New ticket (A11-199), Settings (A11-200) and Plugins (A11-201) pages (`docs/design/atomaut/BRIEF.md`; `docs/design/atomaut/PARITY.md` lists where each feature of the old board is now). The two self-hosted fonts (Inter and JetBrains Mono, bundled from Fontsource) load from the build, and nothing is fetched from another origin.

`ui/` is a private package of its own, **not a pnpm workspace member** (the layout check refuses a `pnpm-workspace.yaml`), with its own `ui/pnpm-lock.yaml`. `package.json`'s `files` does not ship it and `pnpm install --prod` never installs its dependencies, so a machine needs none of them (an install unpacks the tag's source, `ui/` included, and ignores it). **CI builds the UI into each release** (A11-191): `release.yml`'s `ui-build` job checks out the tag the push released, installs `ui/` from its lockfile, builds it and packs `ui/dist` with `scripts/ui-asset.ts pack` into `agent-org-ui-<tag>.tar.gz` (entries sorted, owner 0, mtime 0, `index.html` at the root) and its `.sha256` (`sha256sum` format); `ui-attach` adds both to the GitHub Release, the tarball first. `install.sh` and `agent-org update` fetch and verify them (see "Install"), so no machine ever installs `ui/`'s dependencies or runs `astro build`. `ci.yml`'s `ui` job runs the same install, build and pack on every pull request as a dry run (the tag `dry-run`, uploaded to no Release) and archives the two files as the run artifact `agent-org-ui-dry-run`. `agent-org doctor`'s `ui build` row is `ok` when `/` has a build to serve, and a `WARN` when the running version's release ships one and none is found (the fix is `agent-org update`, which fetches it; in a checkout, `pnpm ui:build`).

To work on it, from the repository root:

```sh
pnpm --dir ui install          # once, and after a change to ui/package.json
pnpm ui:dev                    # the dev server, http://localhost:4321/
pnpm ui:build                  # static files in ui/dist
pnpm ui:typecheck              # astro check (the .astro files) and tsc --noEmit (every .ts and .tsx)
pnpm ui:test                   # rstest: the components, the dev proxy, and the page checks over ui/dist
```

**The dev server proxies `/api/*` to this machine's instance**, so a page can be built against live data. It runs the checkout's own `ticket:remote-info`, which reads the host file (`$AGENT_ORG_HOST`, else the default) and the board key, and passes each call on to `http://127.0.0.1:<port>` with the key in `x-ticket-token`. The key is held in the dev server's memory only: it is never written to a file, a URL, a log line or a response. With no instance or no key the dev server still starts, and a call to `/api/*` answers 502 with `ticket:remote-info`'s own error, which names the remedy (`agent-org ticket:serve` makes the key). Start the instance and call again: no restart is needed.

**The page checks need a build and a browser.** They serve `ui/dist/` with `astro preview` and drive Chromium through `playwright-core`, which `ui/` pins to the root's exact version, the build `onboard` and `doctor` install. They refuse to start, saying so, until `pnpm ui:build` has run. The screenshot helper captures a route at 1440px and at 390px wide, writes full-page PNGs named `<route>-<W>x<H>.png` (A11-151's `captureName`) to `ui/screenshots/` (ignored by git), and fails on horizontal overflow, naming the route, the width, `scrollWidth` and `clientWidth`.

**`ticket:ui` serves the build at `/`** (A11-190 served it under `/next`; A11-202 moved it to the root), behind the pairing and with the remote-instance proxying: a page calls `GET /api/connections` and `/c/<connection>/api/...`, and an unpaired browser is shown the pairing page for any page address (an unpaired call for a file or an instance gets a 401). Every `GET` or `HEAD` that is not an instance call (`/api/...`, `/c/...`) is answered from the build. It looks for the build in `ui-build/` beside the running version (where a release unpacks it), then in `ui/dist/` (a checkout's own `pnpm ui:build`), counting a folder only when it holds `index.html`, on each request, so a build made while it runs is served without a restart. A client-side route is answered with the nearest page above it (`/settings/x` takes `settings/index.html`, else the root page), a missing asset is a plain 404, files under `_astro/` are cached for a year and every other file is `no-cache`. With no build, every page answers a plain 503 page that says the build is missing, that a release carries it and that `pnpm ui:build` makes it in a checkout; the instance's calls still answer. **An address from the days of `/next` is redirected** (`302`, kept out of any cache): `/next` and `/next/<rest>` go to `/<rest>`, with the query, so an old link to `/next/runs/A11-1` still opens its run. **The old board's own links** (it was one page at `/`) land on the page they meant, read in the browser since a server never sees the anchor (`ui/src/shell/old-links.ts`): `/#run-<KEY>` goes to `/runs/<KEY>`, `/#writer-<id>` to `/tickets` (a request card has no address of its own), `/#/settings` to `/settings/models`, and anything else to `/tickets`, each with its `?connection=` kept.

**The instance API's client is `ui/src/api/`** (A11-189): `createClient(connection, { fetch })` has one typed method per route the board calls, and `usePoll(read, { connection })` polls one of its reads. The answers' types are `import type`s from the server's modules (`server.ts`, `ui-server.ts`, `settings-view.ts`, ...), never copies, so a server change that breaks a page fails `pnpm ui:typecheck`. A call never throws: it resolves to `{ ok: true, data }` or `{ ok: false, status, refusal, unreachable }`, where `refusal` is the server's own `error` sentence for a page to show, and every change goes through `mutate`. The client sends what the old board's `call()` sent: a same-origin `fetch` carrying the paired browser's session cookie, and no token of its own (`ticket:ui` adds each instance's key). `usePoll` reads every 5s while the page is visible and pauses while it is hidden. When the page is shown again or the window gains focus it forgets the failures in a row and reads at once. After a failure it waits 2s, 4s, 8s ... up to 60s and starts over on a success. It reports `loading`, `ready`, `empty`, `error`, `unreachable` or `reconnecting`, and keeps the last good data. `unreachable` is for an SSH connection whose proxy answers "cannot reach ..."; `reconnecting` is for a read with no answer or a 502 or 503 (`looksLikeRestart` in `src/ticket-mode/board-view/reconnect.ts`, the rule the old board applied too: an instance or a service restarting, shown as a quiet "Reconnecting…" line and tried again); `error` is for what the server answered with. `readAt` is when the data was read, and `current()` resolves to the held data while it is no more than one poll interval old and otherwise reads now: a page that builds a link from the data (a run's terminal) calls it on the click.

**The Atomaut shell is `ui/src/shell/` and `ui/src/lifecycle/`** (A11-194). Each route is an Astro page (`ui/src/pages/`) that renders the island of its page inside `layouts/Shell.astro`: `/tickets`, `/runs`, `/runs/<key>` (the runs page, which reads the key from the path, since a static build cannot list keys; `ticket:ui` answers it with the nearest page above) and `/settings/<models|workers|machine|plugins>`. `/` goes on to Tickets (or to the page an old link meant) and `/settings` to Models (small pages that keep the query and, for `/settings`, the hash, so `?connection=` still names the instance a link is for). Every page carries its styles inline and no asset is inlined as `data:`, because the instance sends its pages with a policy that allows only inline styles (`PAGE_CSP` in `ui-server.ts`). **Every value is a token in `ui/src/styles/tokens.css`**: `ui/test/tokens.test.ts` refuses a colour literal anywhere else under `ui/src/` and a pixel length (bar a 1px hairline and the one 820px media rule in `shell/shell.css`) in any other stylesheet, so a page ticket adds the tokens its boards need to that file and uses them by name. `ShellProvider` reads once what the sidebar shows and a page reuses it through `useShell()`: `/api/connections` once (the instance shown is `?connection=`, else the one remembered under `ticket-mode.connection`, else this machine's, and a switch gives every read a new client for that instance), `/api/config` and `/api/tickets` once per connection (`usePoll`'s `repeat: false`), and `/api/queue` every 5s, which drives the Runs badge and the connection pill. The shared lifecycle components (`Lifecycle`, `Skeleton`, `EmptyState`, `ErrorState`, `UnreachableFrame`) take the polling hook's result and show the skeleton, the empty panel, the page, the error banner with Retry, or the unreachable frame. The page checks (`ui/test/shell.page.test.ts`) answer `/api/connections` and `/c/<name>/api/...` from a stand-in instance (`ui/test/fixtures.ts`).

**The Tickets page is `ui/src/tickets/`** (A11-196): today's Pick tab, drawn as the four Tickets boards draw it (`docs/design/atomaut/BRIEF.md`). Which tickets show, how they group, what can be picked and what a filter keeps are `board-view.ts`, `assignee-filter.ts` and `label-filters.ts`, imported and never restated. The Assignee scope now lives in `ShellProvider`, so the sidebar's counts, projects and goals follow it as the old board's did; on an instance that reads scopes on demand (`config.scopes`) choosing one reads its pages with `client.ticketsPage`, and who holds the rest (`/api/people`) and the parents the tree nests under (`/api/parents`) are read after the first paint. The page remembers its choices under the old board's own keys (`ticket-mode.open`, `.open-parents`, `.priorities`, `.plan`, `.labels`), so a choice made on the old board holds on Atomaut. The queue options (Plan first, Model, Effort, Change defaults, Reset) sit in a popover behind the Options cog of the queue bar, which shows only while tickets are selected; Queue posts what the Pick footer posts (`keys`, `model`, `effort`, `plan`). New ticket opens the dialog of `ui/src/new-ticket/` (A11-199): the request, Quick or Grill, Auto or Manual placement (Auto leaves the project, repository, goal, priority and parent to the writer; Manual sets the ones chosen and the writer uses them as given), and the writer's model and effort as a pill linking to Settings. The request strip under the header draws each request from `/api/writer` (polled every 5s) in its state: queued, writing, waiting for you, done or failed. The request is held by the page, not the dialog, so closing the dialog stops nothing.

**The update in progress is `ui/src/updating/`** (A11-217): the page left open across an `agent-org update` shows the Updating card (then Slow, then Back) in the main column in place of the page, with the sidebar as last known and the connection pill amber "Updating", and Tickets and Runs carry the drain banner (`updateBanner()`'s words) while a breaking release drains. The page decides it is an update when its queue poll is `reconnecting` and the last good read named one: a drain note, or `update.next`, which `/api/queue` now carries while `update.lock` names a live process (`src/ticket-mode/update-next.ts`: the `.partial` folder being built, else the version `current` names once it is not the running one). Slow is 60 s after the first failed poll; Back is the first good read on another version, and the page reloads itself 5 s later onto that version's code. `node scripts/board-update-check.ts` runs a real throwaway install through a normal and a breaking update in a real browser.

Lint covers `ui/`: `npm run lint` reads `.ts`, `.tsx` and `.astro` with the same Clean Code rules, and CI's `ui` job runs the typecheck, the build and the tests.
